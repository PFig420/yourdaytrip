# planner — day planner and validator (YourDayTrip steps 3 and 4)

Claude **chooses and orders places and suggests stay lengths. Nothing else.** Every time, walk and ride in a plan comes from the reachability engine through the scheduler (`Planner.md`). The model never outputs a clock time, route or trip id.

## Run

The packages are used from the repo (no install needed); `anthropic` is the one extra dependency (`pip install --user anthropic`).

```bash
export PYTHONPATH=planner:places          # from the repo root; engine is already installed (editable)
python3 -m planner plan --from porto-campanha --date 2026-10-24 --after 08:00 --back-by 21:00 \
        --interests history,maritime --pace relaxed [--text "..."] [--weather rain] [--no-llm] [--json]
python3 -m planner plan ... --leave-by 17:30   # instead of --back-by: the first vehicle home leaves by 17:30, it may arrive later (exactly one of the two)
python3 -m mapdata.build                    # offline, model server stopped: OSM paths -> data/paths/ (see mapdata/README.md)
python3 -m planner plan ... --geojson day.geojson   # also writes the day as a GeoJSON map (open it in geojson.io)
python3 -m planner plan ... --debug            # keeps the accepted draft's notes and the failed drafts in the plan (testing)
python3 -m planner plan ... --backend claude-code   # test backend: local Claude Code CLI on the subscription (local use only)
python3 -m planner eval --backend claude-code [--resume]   # Gate 3 quality run, unbilled, sequential
python3 -m planner eval --backend api --estimate    # offline cost estimate for the API run, no call
python3 -m planner eval --backend api --approved    # API cost-and-speed run: only after Pedro approves
python3 -m planner.web [--backend local]  # 127.0.0.1:8300: test page at /, POST /plan[?use_llm=false][&debug=true][&map=true], GET /health, GET /meta; default backend is the billed API
cd planner && python3 -m pytest tests     # 149 offline tests; 3 fail already (test_pl_pack.py, prompt-fix work) (engine/ and places/ tests run separately)
```

`--from` takes `porto-campanha`, `porto-sao-bento`, `aveiro-station` or `lat,lon`. Credentials come from the environment or an `ant auth login` profile through `anthropic.Anthropic()`; nothing is logged or stored. `--no-llm` needs none.

Python: `pl = planner.load(); plan = pl.plan(PlanRequest(...), use_llm=True)` → `DayPlan` (`.to_json()`).

## Decisions

- **Claude Code backend (§2.4).** `planner/claude_code.py`; `backend="claude-code"` in `planner.load` and `--backend` on `plan` and `eval`. Binary: `claude` on PATH, else the newest VS Code extension copy (compared numerically), else `PLANNER_CLAUDE_BIN`; this machine uses `~/.vscode-server/extensions/anthropic.claude-code-2.1.308-linux-x64/.../claude`. One subprocess per call in a fresh empty temp dir, the user message (or the retry history rendered as `[Visitor request] ... [Your previous draft] ...` text) on stdin, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_BASE_URL` removed from its environment, never `--bare`. The web server raises on `claude-code`.
- **Real `--output-format json` fields** (from a tiny call on 2026-10-23, CLI 2.1.308): `type: "result"`, `subtype`, `is_error`, `result` (the answer as a JSON string), **`structured_output`** (the schema-constrained object, used), `usage.{input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens}`, `total_cost_usd` (the CLI's own list-price figure, **not billed**, logged as `notional_usd`), `duration_ms`, `stop_reason`, `terminal_reason`, `api_error_status`, `num_turns`. Input tokens in our logs = plain + cache read + cache creation. `modelUsage` also shows a small Haiku call: the CLI makes its own helper calls, one reason its numbers do not carry over to the API.
- **Backend errors.** An exit code other than 0, `is_error`, unreadable JSON or a missing/invalid `structured_output` is an API-style failure (fallback plan, message kept in the log under `backend_errors`). A message containing "limit", "quota" or a reset time is read as the subscription running out, and "not logged in" / "/login" as a login problem; both set `llm.fatal`, stop retrying and stop an eval run cleanly. The real usage-limit text has not been seen; the match is deliberately broad (a false stop is safe, a false continue is not).
- **Outcomes (§11).** Each request is `llm_valid`, `llm_failed_fallback` or `no_plan`. First-try validity and the fallback share are computed over requests that have a plan at all (`no_plan` excluded, since it measures data and rules); the first-try share over all 50 is also in the logs. A request interrupted by a usage limit is not logged, so `--resume` redoes it.
- **Free time before dinner (§6.1).** A dinner place reached by a walk-only leg (at most 2,000 m) before its window opens, with a gap of at most `max_free_time_min` = 120, gives a `free_time` entry instead of `wait_too_long`. If the free time is 45 minutes or more, one always-open (`24/7`) place from the dinner place's cluster in the pack is inserted if its `visit_min` fits with walk-only legs (and ends before sunset when daylight only), marked `inserted: true`. A gap counts as dinner only when the arrival is outside all the place's meal windows and the dinner window opens within 120 minutes. All `24/7` places in the data are flagged daylight only, so in practice insertions end before sunset.
- **Fallback, dinner.** Meals are judged by when a stop is actually visited, not by what the place serves (a restaurant that serves lunch and dinner but is visited at 13:00 is a lunch). A missing meal is placed by trying each dinner place at each position, then ending the sights earlier, then stretching stays. With this, 49 of the 50 eval requests get a fallback plan; the one `no_plan` is Porto on 8 Dec back by 22:30.

- **Installed SDK: `anthropic` 2.2.0.** `client.beta.messages.parse(...)` accepts `betas`, `fallbacks`, `output_config`, `output_format` and `cache_control` together (checked with the signature and with a mock HTTP transport in `tests/test_pl_pack.py`: the request carries `anthropic-beta: server-side-fallback-2026-07-01`, `fallbacks: "default"`, `output_config` with both `effort` and the JSON schema, `cache_control`, and no `thinking`). So no `create` fallback was needed. `messages.parse` has no `cache_control`, so every call uses the beta surface; `server_fallback = false` in `config.toml` just drops the beta header and `fallbacks`. The SDK uses `httpx2`; tests use `httpx2`.
- **Retry turns keep the model's reply as it came** (its content blocks), then append the error list as a user turn; earlier turns are never edited.
- **A cut-off reply (`max_tokens`) counts as a `schema` error and is retried.** A refusal goes straight to the fallback.
- **Error order.** Schema limits are checked first and short-circuit (more than 6 stops is `schema`, as the spec's unit test says). Pace limits (`too_many_stops` above 4 for relaxed, 6 for packed; `too_few_stops` below 2) and `duplicate_place` are reported together with the scheduling errors. The scheduler carries on after a soft error (a closed place is skipped; a long wait, overrun or short stay still proceeds) so one retry message can list several problems. A leg with no journey, or arriving after `back_by`, stops the chain: later stops are not checked.
- **Rain.** Outdoor places are not in the pack; a draft that names one gets `unknown_place` ("outdoors and the request is for rain"). The spec has no separate code.
- **When meals are required.** Lunch: `leave_after ≤ 12:00` and `back_by ≥ 15:00`. Dinner: `back_by ≥ 22:00` and `leave_after ≤ 19:00`. A meal visit must start inside a meal window of the place; `visit.meal` is `lunch` or `dinner` when it starts in that window.
- **Daylight.** Opening intervals are clipped to sunrise and sunset like the places layer; a visit ending after sunset is `visit_overruns`, tours included (the spec exempts tours from closing time only).
- **Waits are timeline entries.** Gaps of a minute or more become `wait` entries: for opening or entry times, for connections, and between the end of a visit and the walk to the next vehicle (the engine leaves as late as it can).
- **Plan B** covers changes under 10 minutes in every journey of the day, not only the way home. Each is the next journey from the boarding stop one minute after the missed departure; `within_deadline` is set for the way home only. The backup to `last_safe_return` is found by asking for the latest departure that arrives strictly earlier.
- **Warnings** carry only what applies: the engine's coverage warnings, stale hours and draft records for places in the plan, accepted fast legs (matched by trip id in `converter/config/accepted_legs.csv`), clamped stays, and feed-hash differences.
- **"Data as of"** lists each feed's validity window and, where `feed_info.txt` has a version, its build date.
- **Pack.** The sights are the top 12 by score, swapping in the best place of another cluster if they all share one. The food places are every one with a lunch slot (up to 6), filled to 6 by score. Travel hints go in as `travel_minutes` (reference time `leave_after + 3 h`, `max_walk_m = 2000`, pairs over 120 minutes dropped). A normal pack is about 20 kB (roughly 6,000 tokens).
- **Fallback.** Greedy by score: each added stop must schedule cleanly with a valid way home. A meal comes in when the current time is within 90 minutes of its window; a sight is refused if it would leave less than 45 minutes of a window still owed. Stays are `visit_typical` (relaxed) or `visit_min` (packed). If a required meal cannot be placed, a second pass stretches sight stays to 2 × typical. The result is checked by the same validator. If nothing valid is found, the answer is `status = "no_plan"` with the errors, and no timeline.
- **`DayPlan` additions** to the §3.2 list: `status` (`ok` or `no_plan`), `title`, `errors` (when `no_plan`), `attempt_errors` (error codes of each failed draft; used by the eval), `attempt_drafts` (2026-10-27: each failed draft's title, stops with place names, notes, and its errors with messages, for debugging; `draft` is null for a schema failure). Since 2026-10-27 every visit's `reason` is filled in: the model's `why`, or for a fallback plan the shortlist's first two reasons.
- **Narrative.** The check removes the plan's own place names (and the origin's) before looking for any other place name, so it is conservative: a story that mentions another place is dropped. The narrative runs only for `source = "llm"`; a fallback plan has none.
- **`/health`** calls `models.retrieve` once per 5 minutes and never echoes error text.
- **Installing `anthropic`.** The system Python blocks `pip install`; it is installed with `--user --break-system-packages`. A virtualenv would be tidier before deployment.
- **Compact pack (2026-10-26, `selfhostedLLM/Execution.md` M5).** `[pack] profile = "compact"` gives the **local backend only** the `[pack.compact]` values: 8 sights, 4 food, descriptions clipped at a word to 160 characters, travel hints of 60 minutes or less. `Planner.compact_pack` decides it, so the `api` and `claude-code` backends get the full pack byte for byte (`tests/test_pl_compact.py`). The request and `day` block are never trimmed. On the 50 eval requests the first-attempt prompt falls from a median of 8,180 to 4,221 tokens. **Switched on 2026-10-27 (Pedro)**: the full pack needs a 14,336-token context and does not fit the 7.5 GiB laptop with VS Code open. The local `max_tokens` for drafts fell from 2,048 to 800 at the same time, because completed drafts are 276–436 tokens and runaway drafts were costing 6–7 minutes. `test_pl_local.py` pins the full pack, because its scripted golden draft uses full-pack places.

- **Changes of 2026-10-27 (`Changes.md`), choices the brief left open:**
  - **Debug (B).** `DayPlan.debug` is `{draft, attempt_drafts}` and exists only when `plan(..., debug=True)` (HTTP `?debug=true`, CLI `--debug`; the test page and the eval always pass it). It is also set on a `no_plan` result. `attempt_drafts` moved there from the top level; `attempt_errors` stayed.
  - **Free time (A).** The pass is `planner/freetime.py`, called from `Planner._finish`, so `Scheduler.schedule` (and the golden tests that call it) still returns waits; only `plan()` output shows free time. A wait counts as "straight after a visit" when the entry before it is a visit, so the first wait of the day at the origin never converts. The journey home is found from `Result.home_idx`. When the way home has no ride the reason is "free time before the walk home" (the brief only names bus and train). Modes other than `rail` and `bus` use the mode name.
  - **Ideas: opening hours.** A suggestion must be open from the arrival until the end of the stay, and the stay is cut at closing or sunset when that comes first (`minutes_there` is the time left after both walks *within opening hours*, at least `visit_min`). The brief's strict reading (`minutes_there` = all the time left) would exclude every museum that closes during the gap and every daylight place near sunset. `open_until` is the sunset for daylight-only places, `null` only for 24/7 places with no daylight limit; places with fixed entry times (tours) are never suggested; with `include_food` off no food places are suggested; the pre-filter is the crow-fly distance, then `Router.earliest` with the walking limit (`suggest_walk_m`, capped at the engine's 2,000 m).
  - **Costa Nova, 31 Oct: no ideas fit (needs Pedro).** The free time 16:24-18:05 at Canastra do Fidalgo is produced as specified, with no suggestions. `praia-costa-nova` is 1,126 m on foot from Canastra in the place data (the brief says about 250 m), so the 800 m limit rules it out; it also needs 60 minutes (`visit_min`) and sunset is 17:32, which leaves about 48. `costa-nova-palheiros` is 1,311 m. Within 800 m the only confirmed places are two restaurants closed between 15:30 and 19:00; the fish market is a draft record. Raising `suggest_walk_m` would not help the beach on this date; a fix would be place data (its coordinates are marked as estimates) or a shorter `visit_min`.
  - **Leave by (E).** Pedro's answer (2026-10-27, after the first build used "the last visit ends by X"): leaving means **the first vehicle home leaves the destination by X**; the walk to the stop counts before X, the arrival home may be later. `back_by` holds X in both modes; `deadline` says which. `Scheduler.deadlines(req, d)` returns (latest arrival home, leave-by or None). `left_too_late` is checked once, on the journey home: its first ride's boarding time (a walk-only journey: its departure) must be at most X. In leave mode the pack gets the engine window up to `leave_mode_home_by` (or X if later) and `leave_by=X` for the shortlist; hints use X for the reference time and the window end for the scan. A home-mode pack was compared with the pre-change code for all 70 requests in `requests.jsonl` and `holdout.jsonl`, full and compact: 140 packs, byte-identical.
  - **Leave mode: last safe return.** `engine.latest` takes arrival deadlines only, so the planner chains `earliest` journeys forward from the end of the last visit (the next starts a minute after the previous departure) while the first vehicle leaves by X and the journey arrives by `leave_mode_home_by`; the last one is the safe return and the one before it the backup. The pack's per-place `leave_by` is capped at X without subtracting the walk to the stop (optimistic; the validator decides). Nothing was added to `engine/`.
  - **Leave mode: plan B.** `within_deadline` is set for legs before the last visit too (the next journey must arrive by X), and for the way home against `leave_mode_home_by`; home mode is unchanged.
  - **Narrative retry (C).** Only when `backend == "local"` and `[local] narrative_retries` > 0; a retry that itself errors gives the usual "could not be produced" warning; any failure gives exactly one narrative warning. Retry messages come from `narrative.retry_message`.
- **Cut-off local drafts (CurrentChanges R, 2026-10-27).** `LocalBackend.call` raises `BackendError("max_tokens")` with `.partial` (first 4,000 characters of the generated text); `LLM._parse_backend` turns that one kind into a `CallResult` with `stop_reason = "max_tokens"`, `parsed = None`, `raw`, and `backend_error` still in usage. `_llm_loop` then handles it like Claude's cut-off draft. `raw` is stored only in `debug.attempt_drafts` (so only with `debug=True`); Claude cut-offs have no `raw`. Other local error kinds are unchanged and final.
- **Reference points in the planner (CurrentChanges.md P, 2026-10-27).**
  - **Scheduler.** `Scheduler._reach` tries every point of the place with `Router.earliest` from the current position and keeps the earliest arrival (the main point wins a tie); the visit and the way out use that point. Non-main points are routed as `<id>#<k>`, so the engine never sees two coordinates under one id; `Scheduler.point_place` maps such an id back to its place (safe return, plan B). Walk entries name the point, e.g. "Praia da Costa Nova (south end, dune boardwalk from the Costa Nova houses)"; the visit entry keeps the plain place name (the narrative check depends on it). `Result.visit_points` records the point each visit used. `_fill` (the inserted visit before dinner) picks its candidate's point the same way, walking only.
  - **Pack hints** go from a candidate's chosen point (`Item.point`) to every point of the others, shortest per pair; the pack JSON shows no point. For a place without points the engine call is exactly the old one.
  - **Free-time ideas** use the point nearest by walking time and name it in `point` (only for places that have extra points; `null` for the main point). The free time's location is the point its last visit used.
  - **Byte identity.** With the data before this change (no points) the new code gives the same pack as the pre-change code for all 70 requests in `requests.jsonl` and `holdout.jsonl`, full and compact: 0 of 140 differ. With the points in the data, packs of 63 requests (full) and 60 (compact) change. Of those, 73 packs of 123 changed packs include `costa-nova-palheiros` or `praia-costa-nova` as a candidate (earlier arrival, other slots, hints); 48 differ only in cluster labels (the seafront joins Canastra's cluster, which renumbers `cN`), and 2 (`r12`, `r21`, full) differ only in which candidates share a cluster, through the seafront which is not itself a candidate there.
  - **Golden plan changed, as it must.** The scripted golden day ends at the seafront, which now has points: Canastra to the seafront is a 20 m walk (13:49 -> 13:49) instead of the 1.3 km stroll (13:49 -> 14:13), the visit is 13:49-15:04 instead of 14:13-15:28, the home train is 16:23 (home 17:20, was 18:20) and the last safe return leaves by 18:40 (was 18:25). Everything up to Canastra is unchanged. `test_pl_golden.py` and `test_pl_leave.py` were updated for these values; no other golden changed.
  - **Shortlist time** (one call from Porto Campanhã, three dates, fresh cache each): 0.07-0.08 s before, 0.07-0.09 s after.
- **The map (MapPlan.md, 2026-10-27).**
  - **Ids on the timeline** (`Ride.feed/board_stop_id/alight_stop_id`, `Walk.from_id/to_id`, `Visit.point_id`, `FreeTime.point_id`, idea `point_id`) come straight from the engine's legs and the scheduler's chosen point; output only. A test checks that `narrative.payload` is the same with every id blanked.
  - **`mapview.build(plan, engine, lib)`** works from the plan (or its JSON) and the read-only `engine.feeds` / place records. Ride lines use the trip's stop sequence from boarding to alighting (a circular trip is read by the board and alight times, so only the stops between are drawn); a trip it cannot find is drawn stop to stop with a warning. Walks are the straight line between their two ends. Visit numbers `n` count visits in timeline order, inserted ones included. A visit's position is its `point_id`, so a long place shows at the reference point used and `point_name` says which. `bounds_destination` covers the timeline steps from the first visit to the last (visits, rides, walks, stops, free time; not ideas), so the first ride out and the last ride home are left out; with no visits it equals `bounds_all`. The idea property for the place's kind is `place_kind` (`kind` is the feature kind). Wait entries get no feature. An id it cannot place is skipped with a warning; none occurred in the two sample plans.
  - **Exposure:** `DayPlan.map` (default `null`), `POST /plan?map=true` (not for `no_plan`), CLI `--geojson PATH` (a `no_plan` writes nothing and says so on stderr). The eval does not ask for a map.
  - **Page.** Leaflet 1.9.4 from cdnjs (CSS and JS); tiles from `/meta` (`[web] tile_url`, `tile_attribution`, OSM standard by default). If Leaflet cannot load the panel says so and the timeline renders as before. Colours are page tokens (`--m-rail`, `--m-bus`, `--m-ferry`, `--m-walk`, `--m-food`, light and dark); the tiles are unchanged. The plan opens on "Destination" when it differs from "Whole day". Clicking a row (or Enter/Space on it) selects its features, opens the visit's or ride's popup and, only if they are out of view, re-centres with a zoom no higher than the current one; clicking a feature selects its row and scrolls it into view. Food visits (those with a meal) have a different pin colour.
  - **Checks:** the page script passes `node --check`, and `tests/page_harness.js` runs it against a minimal DOM and a stub Leaflet (each feature kind drawn the expected number of times, every row with features mapped, both click directions, keyboard, the panel hidden without a map). The visual check is Pedro's.
- **Phase 2 of the map: paths from OpenStreetMap (MapPlan.md §10, 2026-10-28).**
  - **Design:** an offline cache (`mapdata/`, `python -m mapdata.build`) read at runtime by `planner/paths.py`; rejected: a self-hosted routing server (a Portugal graph does not fit the laptop's free memory; may suit production hardware later), public routing APIs (limits, a network dependency at plan time, terms) and operator shapes (none published). The interface is `Paths.ride(a, b, mode)` and `Paths.walk(a, b)`, so a routing server could replace the cache without touching `mapview.py`.
  - **Display only.** The engine, its walking distances, the times and every check are untouched. A walk popup keeps the timeline's (engine) distance and adds "the street route is about N m" when the path differs by more than 25 %.
  - **Features.** `ride`, `walk` and the new `idea_walk` (an idea's walk from the free time, drawn in the ideas layer) carry `path` (`osm`/`partial`/`straight`) and `gaps` (coordinate index ranges that are straight lines); walks also `path_m`. The page draws a gap as a dotted grey line, so a guess never looks like a route. A ride's cached pairs are joined in order (a missing pair falls back to the straight segment for that pair only); a walk is looked up by `from_id`/`to_id` and reversed when only the other direction is stored; a walk between arbitrary coordinates stays straight.
  - **Missing or stale cache:** straight lines and one warning; a cache whose `meta.feeds` differ from the engine's feed hashes is ignored with a warning. `meta.places_hash` is stored but not checked at runtime (a new place point simply has no cached walk and falls back).
  - **Selection:** the selected leg is drawn on top with a white outline (casing) and a stronger stroke, the rest of the day is dimmed to 40 %; clicking the same row or feature again, or Escape, clears it.
  - **Build choices where the brief left room:** one `highway` download per tile (the bus and foot graphs are both derived from it with per-edge flags), not three layers; the railway layer also includes `railway=narrow_gauge` (the Vouga line Aveiro-Águeda is tagged that way; with only `rail` and `light_rail` 66 rail pairs had no path); the "engine underestimates" flag also needs the path to be at least 100 m longer (otherwise opposite-side bus stops 20 m apart flag as "infinitely" longer); a snap beyond its limit but within 3 times it is kept and flagged; pairs where both ends are outside the corridor are not cached (a CP trip's Lisbon-side stops draw as straight segments); a zero-length pair is not ratio-checked.
- **Walking overrides (WalkBarriers.md, 2026-10-28).** The engine now takes the longer of its estimate and the OSM path for every cached walk (`ReachabilityEngine.md` §5.4, `mapdata/README.md`). Effects here: walk legs report the OSM metres, free-time ideas and plans see the real walking lengths (Sé de Aveiro -> Museu de Aveiro is 94 m straight but 373 m on foot, so a 30 minute gap no longer fits it; the Costa Nova beach point is 478 m, not 345 m), and the home leg ends with a few-metre walk from the station stop to the origin point (4 m at Porto Campanhã). Fix found on the way: the pack's travel hints used the main place id with a reference point's coordinates, so the wrong override could apply; the hint now starts from the chosen point's own id (`#k`). Tests changed for these reasons only: `test_pl_freetime.py` (beach 478 m, the Sé idea), `test_pl_leave.py` (the last ride, not the last entry, is the train).
- **Phase 3 of the map: buses on their mapped route (MapPlan.md §11, 2026-10-28).**
  - `meta.ride_source` says per bus stop pair whether the cached path is `relation:<id>` or `shortest`; `Paths.ride_source` reads it and `mapview` sets `route_source` on bus rides: `relation` when every pair is, `mixed` when some are, `shortest` when none is (a pair with no cached path does not count as a relation pair). Rail, the ferry and a cache without sources give an empty `route_source`, so the page claims nothing there. Display only; `path` (`osm`/`partial`/`straight`) is unchanged.
  - Page: one popup line ("Route: as mapped in OpenStreetMap" / "partly ... partly the shortest road path" / "shortest road path between stops (this line is not mapped in OpenStreetMap)") and the new legend sentence; no new line styles.
  - Build choices: a stop may pass a relation piece more than once (out and back, loops), so every pass within 40 m is tried; where several lines share a stop pair the shortest valid piece of any of their relations is used (the cache key is the pair, not the line); the 2 x test is skipped when a pair has no shortest path to compare with; the Transdev relation for line 36 is matched as the brief's table lists it (it is old and may be wrong: see the report).

## Known limitations

- Dinner days from Porto can still be `no_plan` (e.g. Porto, 8 Dec, back by 22:30): the last trains and buses leave too early to fit dinner and the way home.
- Hints and the pack come from the places shortlist, which only uses confirmed records (78 on 23 Oct 2026; drafts are excluded).
- After 2026-12-12 CP trains are missing; plans from Porto then say so and usually come back `no_plan`.
- The wait limit (45 min) and the walking limit between places (2,000 m) come from the spec; both are in `config.toml`.
- `costa-nova-palheiros` sits at the north end of the seafront (spec §14); the 2,000 m limit keeps plans sensible.
- Prices in `eval/prices.toml` are from the model table cached 2026-10-06; cache writes are costed as plain input.
